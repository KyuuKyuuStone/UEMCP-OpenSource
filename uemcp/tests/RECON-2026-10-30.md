## 任务 A：P1-5「会话太脆」—— 复现成功，但根因与对方判断不同

### A.0 环境与工具

- Server：`node uemcp\packages\server\dist\index.js --transport http --port 19190 --policy standard`（审计目录隔离）
- 复现脚本：Node `session_repro.mjs`（fetch；每次迭代：initialize → notifications/initialized → tools/list；A2 变体在 initialize 后 GET /mcp SSE 读完首个事件即 abort）
- 过程披露：第一轮脚本因**我方参数错位 bug**（body 错传给未使用的 method 形参、headers 对象错传给 sid）把 `mcp-session-id: [object Object]` 发给服务器，全部 404——该轮数据作废，已修正重跑（修正后 curl 单发 initialize 200+sid 验证服务器正常）。

### A.1 实测结果

| 实验 | 结果 |
|------|------|
| **A1 基线**（20 轮 initialize→notify→tools/list，不开 SSE） | **20/20 全 OK，0 失败** |
| **A2**（20 轮，initialize 后 GET SSE 读首个事件即断开） | **前 12 轮全 OK**；第 13 轮起 initialize 开始 429 |
| **A3 sessions 泄漏观测** | A1+A2 共 32 次 initialize 后 `/health` 显示 **`sessions: 32`（=MAX_SESSIONS 满）**，此后 initialize 一律 **429 -32012 "Too many concurrent sessions (max 32)"**，直到 TTL（30 分钟）或 DELETE |
| **A4 TTL 曲线**（`--session-ttl-ms 3000 --session-sweep-ms 1000`） | t0=200 OK → **t+1.5s=200 OK**（活动重置 TTL）→ **t+5s=404 -32001 "Session not found"**（服务器日志 `session_expired`）——静默失效精确复现 |
| **A5 DELETE 曲线** | DELETE /mcp → 204；同 sid 再 tools/list → **404 -32001 "Session not found"**（正常路径确认） |

### A.2 定性（与对方报告的差异）

1. **对方的机理假设不成立**："HTTP 客户端读完 SSE 就断开 → 服务端把 session 删了"——A2 证明 **GET SSE 断开后 session 存活**（断开后 notify/tools/list 正常到第 12 轮）。`http.ts` 的 `transport.onclose`（**L293-297**）只在**整个 transport 关闭**（DELETE /mcp、TTL 清扫、进程退出）时触发，GET SSE 单连接断开不会。
2. **真正的缺陷形态（两个，均已实测）**：
   - **会话池只增不减**：每个 initialize 创建一个 streamable session，只有 TTL（默认 **30 分钟**）/DELETE 能回收。反复重连（外部的"偶发"测试、任何重试风暴）**32 次即满仓**，之后 initialize 一律 429。对方若观察到"initialize 后立刻 SESSION_NOT_FOUND"，最可能是**满仓 429 无新 sid 时客户端沿用旧 sid**、或**测试周期跨过 30 分钟 TTL 旧 sid 静默失效**（A4 复现）——两者都不是"立刻"发生，而是**状态累积**的结果，与"偶发 2 次"吻合。
   - **TTL 静默失效**：30 分钟无活动（或绝对老化）后清扫，旧 sid 一律 404 -32001，**客户端没有任何提前通知**（服务器日志有 `session_expired`，但 MCP 通道无推送）。
3. **"initialize 后立刻 notify 失败"未复现**：A1/A2 各 20 轮，notify 失败 0 次。若对方能提供其复现时的 `/health sessions` 值与时间跨度，可进一步对号入座。

### A.3 根因定位（行号）

- `uemcp/packages/server/src/transports/http.ts`
  - **L286-297**：initialize 创建 transport + `onsessioninitialized` 入 map + `onclose` 删 map（仅整 transport 关闭时）
  - **L303-307**：未知 sid → 404 -32001 "SESSION_NOT_FOUND"（对方看到的报错形态）
  - **L282-285**：`sessions.size >= MAX_SESSIONS(32)` → 429（满仓形态）
  - **L393-405**：TTL 清扫器（`opts.sessionTtlMs`，默认 30 分钟，config.ts L112-114；`session_expired` 日志）
- SDK 层：`StreamableHTTPServerTransport`（GET SSE 断开不触发 close）——已由 A2 实测反证。

### A.4 建议修法（供 Server 岗裁量，未改代码）

1. **会话回收**：`transport.onclose` 之外增加"无活跃 SSE 流且 N 分钟无 POST"的降级回收；或 streamable session 在 `initialize` 响应写完且未开 GET 时用更短 TTL（区分"活跃流会话"与"裸 POST 会话"）。
2. **429 改善**：满仓时按 lastSeen 逐出最老 session（LRU）而非直接拒绝，响应体带 `retryAfterMs` 与 `sessions` 现值。
3. **失效可见性**：initialize 响应体或 /health 已含 TTL；建议 tools 响应头加 `mcp-session-expires-in`，客户端可预判。
4. **文档**：§3.3 注明"TTL 30 分钟静默失效、32 会话上限、重连客户端应在收到 404 -32001 后自动重新 initialize"（客户端遵循 MCP 规范重连即可自愈——外部团队若实现了重连，偶发 404 本不该成为问题）。

## 任务 B：P1-6「备份目录顶替插件」—— 复现成功，机理为"发现顺序"

### B.1 实验（TEXT_54，zip 装机真插件 + 伪造备份目录）

| 轮 | 备份目录 | 日志证据（LogPluginManager） | 实际加载 |
|----|----------|------------------------------|----------|
| B1 | `Plugins\UEMCPBridge_backup`（排序在真插件后） | `The same version (v1) of plugin 'UEMCPBridge' exists at '…\Plugins\UEMCPBridge\UEMCPBridge.uplugin' and '…\Plugins\UEMCPBridge_backup\UEMCPBridge.uplugin' - **second location will be ignored.**` | **真插件生效**：`__pycache__` 仅在真插件目录出现、init_unreal.py 从 `Plugins\UEMCPBridge\…` 运行、bridge 正常启动（18778） |
| B2 | `Plugins\AAA_UEMCPBridge`（排序在真插件**前**） | `… exists at '…\Plugins\AAA_UEMCPBridge\…' and '…\Plugins\UEMCPBridge\…' - **second location will be ignored.**`（**被忽略的变成了真插件！**） | **备份目录顶替成立**：无 UEMCPBridge 的 init_unreal 运行记录（备份目录内无该文件）→ **bridge 完全没启动**（health 18778 DOWN） |

- B2 中 bridge 未启动的原因：我构造的备份目录只含 `.uplugin` + `settings.py`（无 init_unreal.py）——**被 mount 的是无功能的备份目录**，直接证明了"引擎 mount 谁，谁就是插件"。
- `/health sourcePath`：字段存在但**返回空串**（B1 实测 `sourcePath=""`，buildHash 同空）——`_PLUGIN_ROOT` 在"项目内安装"形态下未赋值。**该字段当前不可用于判定**，我改用 `__pycache__` 位置 + init_unreal 运行路径 + 日志行三重证据（已向 Bridge 岗记一次字段缺陷）。
- 会话事故记录：B2 首跑被用户编辑器占用（按规则等待）；第二次撞上我的 240s 等待窗口不足（编辑器启动慢）而超时退出——编辑器留在后台继续跑完，本轮从其日志取到完整证据后关闭。

### B.2 定性

**成立。** 引擎对 `Plugins/` 下同名（.uplugin 内 Name 字段相同）插件按**发现顺序**取第一个 mount，其余一律 `second location will be ignored`——**与目录用途无关，排序在前者胜**。对方团队的备份目录只要字母序/扫描序排在真插件前（`UEMCPBridge.bak`、`_backup`、`AAA_*` 均可能），旧代码就顶替新版。B1/B2 的镜像结果直接证明了机理。

### B.3 防坑建议（给对方与 Bridge 岗）

1. **备份绝不放 `Plugins/` 下**——移到工程外（`<project>\..\backups\`）或至少目录名避免被扫描（引擎只扫 `Plugins/*/`*.uplugin 一层，备份要放 `Plugins/` **之外**才绝对安全）。
2. `.uplugin` 防呆：备份目录内**不要保留同名 `.uplugin`**（改名 `UEMCPBridge.uplugin.bak` 即可避免被识别）。
3. 加载检查：启动后查日志 `second location will be ignored`（本报告 B1/B2 的 grep 命令可复用）；Bridge 侧 `sourcePath` 字段修复后（当前返回空串，见 §B.1 末条）可作为运行时自证。
4. 给 Bridge 岗的缺陷单：`health_payload` 的 `sourcePath`/`buildHash` 在项目内安装形态返回空串（`_PLUGIN_ROOT` 赋值路径只覆盖引擎/市场安装形态？）——需补齐，否则运行时自证不可用。
