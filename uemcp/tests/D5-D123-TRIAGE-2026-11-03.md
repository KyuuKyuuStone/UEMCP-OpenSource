**实验受阻的诚实声明**：本机可控工程无 UMG 资产，且 **5.x Python 不暴露 widget-tree 编辑 API**（三个独立路径实测全败）——无法在最小工程里造出"可见的 screen-space UWidget"。因此 D5 最终定性采用 **代码级证据 + 对方证据交叉验证**（下节），不引用脱离证据的理论。

### 1.2 定性（代码级证据 + 对方证据交叉验证）

**0.1.4 包内 `viewport.py` 源码（zip 解出，逐字引用）**：

```python
"""TakeHighResScreenshot(..., bForceGameView=True) synchronously toggles
the level viewport into game view before scheduling the capture.  That toggle
is the part that misbehaves on PixelStreaming projects (the game viewport
there belongs to the streaming path), so the handler never forces game view
for ``level_viewport`` captures."""
```

- **Bridge 岗自己的实现注释承认**：PixelStreaming 项目的 game viewport 属于推流路径——即**编辑器窗口呈现的画面 ≠ scene-renderer 输出**。
- 引擎渲染分层（由该注释与本岗 10-30/11-03 的截图行为实测共同支撑）：`take_high_res_screenshot` 走 **FSceneRenderer 离屏渲染**；screen-space `UWidgetComponent(EWidgetSpace::Screen)` 的绘制属于 **Slate/game-viewport 合成层**，在 scene renderer 之后叠加——**不进 hires 截图**。
- **对方证据与此完全自洽**：hires PNG 0 标记（scene renderer 层）vs 同一时刻窗口截屏 25 标记（Slate 合成层）——两图差异正是这两条渲染路径的差异。

### 1.3 结论（直接回答对方问题）

**监测点标记确实在 UE 侧渲染（对方主张正确），但在 Slate/game-viewport 合成层，不进 `take_high_res_screenshot` 的输出。** P0-1 应重开，且对方给的三个选项中 **②（`method:"window"` 窗口截屏模式并返回同样的 sha256/stats）最务实**——0.1.4 的 viewport.py 已具备全部配套（`stats`/`sha256`/`partial` 管线），窗口模式只是换一个取图源；①（Slate 合成）实现成本高且 PixelStreaming 下行为更不可控；③（文档声明）无论如何都应同时做。
